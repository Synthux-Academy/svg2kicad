# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Converts Illustrator SVG artwork into KiCad PCB `gr_poly` shapes — an outline shape becomes `Edge.Cuts`, everything else becomes openings on a chosen KiCad layer (default `F.Mask`), and compound letter paths (O, B, P, D…) get their counter-holes bridged into ring polygons so KiCad renders them as holes, not solid disks.

There are **two independent implementations of the same conversion algorithm**, not a shared library used by both:

- `svg2kicad_cli.py` — a Python CLI using `svgpathtools`, writes a `.kicad_pcb` file to disk.
- `converter.js` + `ui.js` + `index.html` + `styles.css` — a static, dependency-free web app (no server, no build step) that does the same conversion in the browser and copies the result to the clipboard for pasting directly into KiCad's PCB editor.

**Any change to the conversion algorithm (sampling, ring-bridging, layer/outline detection, degenerate-shape filtering, output format) must be made in both `svg2kicad_cli.py` and `converter.js` by hand.** They are not required to byte-match, but should stay behaviorally equivalent — see "Sampling differs by design" below for the one intentional divergence.

## Commands

Run the CLI (requires `pip install svgpathtools`):
```bash
python svg2kicad_cli.py input.svg [output.kicad_pcb]
```

Run the web app — no build/install step, it's plain static files:
```bash
open index.html
```

There is no test suite, linter, or build tooling in this repo. To sanity-check a change to `converter.js`, load `index.html` in a browser and drive `window.Converter` from devtools:
```js
const result = window.Converter.parseSvg(svgText);
console.log(result.stats); // { edgeCount, maskCount, layerCounts, ringCount, skipped }
```
Compare those counts against the CLI's four printed lines (`Edge.Cuts:`, `F.Mask:`, `Ring polys:`, `Skipped:`) for the same input file — they should match — plus, for each named layer with shapes (see "Role detection" below), its `TouchCopper:`/`TouchBlack:`/`LEDWindow:` line against `layerCounts`. `maskCount` / the `F.Mask:` line count only the *other* artwork, not shapes on a named layer. For anything more thorough, a real browser session (e.g. via Playwright) can call `window.Converter.parseSvg`/`renderKicadText` directly against a real `index.html` page loaded over `file://`, since `getTotalLength()`/`getPointAtLength()` need a real rendering engine (jsdom doesn't implement them).

## Architecture

### Shared domain logic (implemented twice)

- **Role detection (outline + named layers)**: every shape gets a role from its Illustrator layer name, produced by naming layers in Illustrator and exporting with **Object IDs → Layer Names**. `EdgeCuts` → board outline; `TouchCopper` / `TouchBlack` / `LEDWindow` → artwork pinned to a fixed LED-window mode (`touch` / `covered` / `front` — `LAYER_MODES` in each file), whatever the global layer / LED-window settings say; anything else is "other artwork" (`maskSegs`/`mask_segs`, as before) and follows those settings. Ids are normalized (`normId`/`norm_id`: lowercased, non-alphanumerics stripped, so `EdgeCuts_1_` → `edgecuts1`, `LED_Window` → `ledwindow`) and substring-matched. Illustrator puts a layer's name on its `<g>` (on the root `<svg>` for a one-layer file), or directly on the object when it's the layer's only object, so `shapeRole`/`shape_role` checks the shape's own `id` first, then each ancestor's, and the nearest match wins — sublayers work, and every object on a multi-object `EdgeCuts` layer counts as outline (before this ancestor lookup existed, only the object's own id was read, so they didn't). Only when no id on the way up matches does the legacy rule apply: `class` containing `cls-2` → outline (Illustrator's old auto-generated style class, not something the user names directly). It must stay last: Illustrator's Internal CSS export numbers classes `cls-1`, `cls-2`, … per style, so a touch pad can carry `cls-2` and the named layer has to win. (A CLI-only bug once checked `cls-2` alone, so every file using the id-based convention silently produced zero outline shapes — both implementations must check ids first.) The ancestor walk is where the implementations differ: JS just follows `parentNode`; in Python, `svg2paths2()` flattens the document and drops parent groups, so `tag_shape_roles` walks the minidom DOM first, stamps each shape's role into a `data-svg2kicad-role` attribute (`ROLE_ATTR`), and hands the re-serialized SVG to `svg2paths2()` as an `io.StringIO` (svgpathtools accepts file-like input; 1.8.0 does), so the role comes back in each shape's attribute dict. It's minidom on purpose — `svg2paths2()` parses with minidom and matches tags by qualified name, and an ElementTree round trip re-serializes every tag with a namespace prefix (`svg:svg`, `svg:path` once svgpathtools is imported), which makes `svg2paths2()` find no `svg` element and crash.
- **Input shape elements**: Illustrator doesn't always export artwork as `<path>` — a shape made only of straight lines can come out as `<polygon>` (or, less commonly, `<rect>`/`<circle>`/`<ellipse>`/`<polyline>`), and it's easy for one implementation to quietly only handle `<path>` while the other doesn't. The two implementations get parity here through *different* mechanisms, which is intentional, not something to "fix" into matching code paths:
  - **Python**: `svg2paths2()` is called with its `convert_polygons_to_paths`/`convert_rectangles_to_paths`/`convert_circles_to_paths`/`convert_ellipses_to_paths`/`convert_lines_to_paths`/`convert_polylines_to_paths` flags at their **default of `True`**, so `svgpathtools` converts every basic shape into an equivalent `Path` of `Line`/`Arc` segments *before* `convert()` ever sees it — `id`/`class` are preserved on the converted path's attributes. This means `convert()` only ever needs to loop over `<path>`-shaped objects. **Do not add a second element-walking loop for `rect`/`circle`/`polygon`/etc. to the Python side** — every basic shape is already present in `svg2paths2()`'s output, so a second loop double-processes them (this was shipped and caught once already: it doubled `F.Mask` counts on any file with polygons). (`tag_shape_roles` does walk every shape tag, but only to stamp a role attribute before `svg2paths2()` runs — it produces no geometry, so it isn't that second loop.)
  - **JS**: there is no such conversion library, so `converter.js` has a genuinely separate loop over `doc.querySelectorAll('rect, circle, ellipse, polygon, polyline')` (`parsePointsAttr`, `rectToPts`, `ellipseToPts`), run in addition to the `<path>` loop, feeding the same edge/mask routing and `MIN_DIM_MM` filtering. This loop is required in JS and would be redundant in Python — that asymmetry is the point, not a gap.
  - Basic shapes are never compound (SVG holes require multiple subpaths inside one `<path>` `d`), so both implementations always treat them as a single simple contour — no ring-bridging path applies to them.
- **Compound-path / ring bridging**: a raw `d` string is split into subpaths on the `Z...M` boundary (regex: `(?<=[Zz])\s*(?=[Mm])`, handles `ZM` with no space). Each subpath is sampled into points, filtered by a minimum size (`MIN_DIM_MM = 0.02`), then the surviving candidates are sorted by signed area. The candidate with the largest |area| is the outer boundary; every other candidate (same-winding islands first, then holes) is joined into it one at a time via nearest-point rotation (`make_ring_polygon` / `makeRingPolygon`), so letters with several counters (B, 8, %) keep all their holes. Each join is a true zero-width keyhole: both loops are closed back to their start point, so the bridge is the same edge traversed out and back. (Earlier versions bridged only the two area extremes and silently dropped any middle candidate — e.g. the B's upper hole — and used a non-zero-width bridge that could self-cross once a second hole was added.) A compound path still counts as one ring polygon in the stats, however many holes it has.
- **Units**: `SCALE = 25.4 / 72` converts raw SVG `d`-attribute units (assumed to be points, Illustrator's default) to mm. Neither implementation applies `viewBox` scaling — both operate directly on raw path coordinates.
- **Per-element `transform`**: Illustrator can't express a rotated/skewed `<rect>`/`<circle>`/`<ellipse>` (and occasionally `<path>`) in the element's own x/y/width/height attributes, so it emits a `transform` attribute instead — commonly `translate(...) rotate(...)` when a shape was turned as a group before export. Both implementations parse that attribute (`parseTransform`/`parse_transform`: any combination of `translate`/`rotate`/`scale`/`skewX`/`skewY`/`matrix`, composed left-to-right per the SVG spec into a single 2x3 affine matrix) and apply it (`applyTransform`/`apply_transform`) to that element's sampled points before `MIN_DIM_MM` filtering, ring-bridging, and the anchor shift — same ordering rule as those. The matrix's `a/b/c/d` terms are dimensionless ratios and apply directly to already-mm-scaled points; its `e/f` translation terms are in raw SVG units, so they're multiplied by `SCALE` first to match. An element with no `transform` attribute is unaffected (identity matrix). This does not extend to `viewBox` or to a `transform` on an ancestor `<g>` — only the shape element's own attribute is read.
- **LED window** (CLI `--led-window front|back|both|touch|covered`, web app checkbox + select): replaces the single artwork layer with `F.Mask`, `B.Mask`, both, `F.Cu` + `F.Mask` (`touch`, an exposed touch pad), or `F.Cu` alone (`covered`, a touch pad that stays under solder mask) — `LED_WINDOW_MASKS` in each file — writing every artwork shape once per mask layer, plus one keep-out `zone` per entry in a parallel hole-free contour list (`keepout_segs` / `keepoutSegs`). That list holds each simple shape as-is and, for compound paths, the outer contour plus same-winding islands (`split_by_winding` in Python) — holes are filled, since a zone outline can't hold a keyhole cleanly and a copper island inside a counter would be pour-removed anyway. Zone layers are always `F.Cu` + `B.Cu` plus the chosen non-copper layers, deduped so touch/covered mode doesn't list `F.Cu` twice (`led_window_zone_layers` / `ledWindowZoneLayers`) — for `covered` this means the zone layers are just `F.Cu` + `B.Cu`, since its only mask entry *is* `F.Cu`; the keep-out rules and the `(placement …)` token mirror a KiCad 10 copy of a hand-made LED window. `parseSvg` returns `keepoutSegs`; `renderKicadText(edgeSegs, maskSegs, artworkLayer, scale, ledWindow, keepoutSegs, anchor, layerSegs)` takes `ledWindow` as `null`/`'front'`/`'back'`/`'both'`/`'touch'`/`'covered'` and ignores `artworkLayer` when it's set (`ui.js` disables the layer dropdown to match). Named `TouchCopper`/`TouchBlack`/`LEDWindow` layers (see "Role detection") reuse these same modes, masks and zone rules per layer, always on and independent of this setting: `parseSvg` returns them in `layerSegs` (`{ [name]: { mode, maskSegs, keepoutSegs } }`; Python `layer_segs`, `{ name: { 'mask', 'keepout' } }`), and both renderers write them after the other artwork. While it's on, the KiCad-shapes preview also draws each `keepoutSegs` contour on top with a blue outline and a diagonal-hatch `<pattern>` fill, mimicking KiCad's rule-area look. Any artwork group in `touch` or `covered` mode (the other artwork under that setting, or a `TouchCopper`/`TouchBlack` layer) is drawn copper-colored with the same style of diagonal hatch (`.kicad-copper-shape` / `#copperHatch`) instead of the usual solder-mask teal, since that artwork is F.Cu either way — the preview can't tell touch from covered, since it draws each group's `maskSegs` once regardless of how many real layers get it (see below); every other mode keeps the teal fill.
- **Anchor point** (CLI `--anchor none|top-left|top-center|top-right|middle-left|center|middle-right|bottom-left|bottom-center|bottom-right`, web app select, default `top-center`, persists across file uploads within a session — see `ui.js` below): KiCad's paste (Ctrl/Cmd+V) anchors pasted clipboard content at its own coordinate (0, 0), so whichever point of the pasted geometry sits at (0, 0) is what tracks the cursor. By default the output keeps the SVG's own coordinate origin at (0, 0), which is usually not a useful paste point. Setting an anchor computes one of nine named points (`ANCHOR_POINTS` in each file: the four corners, four edge midpoints, and center) of a bounding box — the board outline's (`edge_segs`/`edgeSegs`) if there is one, else all artwork's combined bbox, other artwork and named layers together (`bbox_of` / `combinedBBox`) — and shifts every output point (`edge_segs`, `mask_segs`, `keepout_segs`, and each named layer's segs alike) by the same amount so that point lands exactly at (0, 0) (`shift_pts` / `shiftPts`). This shift is computed and applied at the *original* SVG size, before scaling — same ordering rule as `MIN_DIM_MM` filtering above — so the anchor point ends up at (0, 0) regardless of the scale factor (0 × anything is still 0). In the CLI this happens once, in `convert()`, right before the final `gr_poly`/`zone` text is built; in the web app it happens inside `renderKicadText(edgeSegs, maskSegs, artworkLayer, scale, ledWindow, keepoutSegs, anchor, layerSegs)` itself (`anchor` was an added trailing param, as `layerSegs` later was), since — like scale — re-deriving it from the already-parsed segs is cheap and it must re-run on every anchor-dropdown change without a full re-parse. KiCad's Y axis increases downward, same as this codebase's SVG/mm space throughout, so "top" is consistently the min-Y edge in both implementations — no flip needed. The anchor shift is a uniform translation, so it's invisible in the KiCad-shapes preview (which re-fits its `viewBox` to whatever it's given) — the preview is intentionally left unchanged by this setting.
- **Output**: a full `(kicad_pcb (version...) (generator...) (general...) (paper...) (layers...) <gr_poly items>)` document (see `HEADER` in each file for the exact layer table). Outline shapes render unfilled with `width 0.05` on `Edge.Cuts`; artwork shapes render filled with `width 0` on whatever layer was selected (named layers: their mode's fixed layers). Item order, the same in both implementations: outline, the other artwork (plus its keep-outs in LED-window mode), then each named layer's artwork and keep-outs in `LAYER_MODES` order — so a file with no named layers produces exactly the same output as before they existed.

### Sampling differs by design

- Python (`path_to_pts`) samples **per Bezier/Line segment** from `svgpathtools`, each with its own point count (`clamp(length_mm/0.05, 4, 512)`). Since basic shapes arrive pre-converted into `Line`/`Arc` segments (see "Input shape elements" above), a `<circle>` or `<rect>` is sampled by this exact same per-segment logic with zero shape-specific code.
- JS (`sampleSubpath` in `converter.js`) samples **per whole subpath** using a single hidden, persistent `<svg><path></path></svg>` and `getTotalLength()`/`getPointAtLength()` — no bezier-math library needed, but no per-segment breakdown either. Constants: `mmPerSample = 0.05`, `minPoints = 8`, `maxPoints = 2000`. `ellipseToPts` reuses these same three constants against a Ramanujan circumference approximation (there's no bezier segment to measure, so it treats the whole circle/ellipse the way `sampleSubpath` treats a whole `<path>` subpath). `parsePointsAttr` (polygon/polyline) and `rectToPts`'s straight corners need no density decision at all — the vertices/corners themselves are the shape; only `rectToPts`'s rounded corners are arc-sampled, at a fixed 8 segments per corner.

This means the two implementations won't produce byte-identical polygons for the same input, but should be visually/functionally equivalent for PCB artwork. If you need to change sampling density, the JS constants live at the top of `converter.js`; the Python ones are `path_to_pts`'s default args and the `max(4, min(512, ...))` clamp.

### converter.js / ui.js split

- `converter.js` is pure conversion logic with zero DOM-UI coupling (aside from the one hidden sampling `<path>`), exposed as `window.Converter = { parseSvg, renderKicadText }`.
  - `parseSvg(svgText)` is the expensive step — parses and samples every path once, returns `{ edgeSegs, maskSegs, keepoutSegs, layerSegs, stats }`. `maskSegs`/`keepoutSegs` hold only the other artwork; shapes on a named layer are in `layerSegs` instead (see "Role detection" and "LED window" above).
  - `renderKicadText(edgeSegs, maskSegs, artworkLayer, scale, ledWindow, keepoutSegs, anchor, layerSegs)` is cheap and pure — re-run this on every layer-dropdown or scale-field change, never re-parse. `scale` defaults to `1` (1:1) and is applied uniformly to every output coordinate as a final multiply-and-round step in `grPoly`/`gr_poly` output (via `scalePts`/`scale_pts`), after the points→mm conversion and after `MIN_DIM_MM` filtering — filtering always happens at the original SVG size, not the scaled size, in both implementations.
- `ui.js` owns all DOM wiring: drag-and-drop + file input, the LED-window checkbox + mode `<select>` (shown only when checked; disables the layer dropdown), the layer `<select>` (a "common layers" `<optgroup>` always visible, a "more layers" `<optgroup>` behind a disclosure toggle — the full list mirrors `HEADER`'s layer table), the anchor-point `<select>` (nine named positions plus `none`; defaults to `top-center` via the HTML `selected` attribute, and — unlike the layer/scale controls — is deliberately *not* reset in `resetForNewFile`, since it's a paste-alignment preference the user sets once and expects to carry over to the next SVG they drop in), the scale `<input type="number">` (resets to `1` on every new file), stats display (`showLayerStats` adds one row per named layer that has shapes, above the artwork row, which is then relabelled "Other artwork" — a file with no named layers looks as before), the copy button, and the two live previews.
- **Layout**: `index.html` is a `.app` flex row of a fixed-width `.sidebar` (dropzone/stats/controls, scrollable) and a `.preview` column (flex-grow) holding two `.preview-panel`s, one per preview below. Below 900px (`styles.css` media query) `.app` stacks vertically and the sidebar drops its fixed width.
- **Previews** (`ui.js`, rebuilt once per file load in `handleFile` — the KiCad one also on LED-window toggle via `updatePreview` — not on every layer/scale change, see below):
  - **SVG source** (`showSourcePreview`): the raw uploaded SVG text wrapped in a `Blob`/`URL.createObjectURL` and shown via `<img>` — never `innerHTML`, so embedded `<script>`/event-handler attributes in an untrusted SVG never execute. The previous object URL is revoked in `resetForNewFile` on the next upload to avoid leaking blob URLs.
  - **KiCad shapes** (`showKicadPreview(edgeSegs, groups)`): builds a plain inline `<svg>` directly from `parseSvg()`'s `edgeSegs` and a list of artwork groups `{ mode, maskSegs, keepoutSegs }` — the other artwork under the current LED-window mode, plus each `layerSegs` entry (the same mm-space point arrays `renderKicadText` consumes) — outline shapes as unfilled `.kicad-edge-shape` polygons, artwork as filled `.kicad-mask-shape` polygons (or, for a group in `touch`/`covered` mode, `.kicad-copper-shape` — see above), `viewBox` auto-fit to their combined bounding box. It does **not** go through `renderKicadText`/the `.kicad_pcb` text. Ring-bridged hole polygons (outer + holes joined by `makeRingPolygon`) render correctly as an annulus with either SVG fill rule, because the bridge segment is traversed twice in opposite directions and cancels itself out visually — no `fill-rule` override needed. Keep-out zones are drawn hatched (`.kicad-keepout-shape` + `#keepoutHatch` pattern) — the other artwork's only while LED window is on, a named layer's always. This preview does not need rebuilding when the layer dropdown or scale field changes (see `renderKicadText` doc above) — it only depends on `edgeSegs`/`maskSegs`/`layerSegs`, which `updateOutput()` never touches.
- **Clipboard copy is three-tiered** (in `ui.js`), because `file://` pages have inconsistent Clipboard API support: try `navigator.clipboard.writeText()` first, fall back to a hidden off-screen `<textarea>` + `document.execCommand('copy')`, and as a last resort make that same textarea visible so the user can manually Cmd/Ctrl+C. Don't replace `execCommand` without keeping an equivalent last-resort tier — it's deprecated but still the only thing that reliably works with zero permissions.
- Plain `<script defer>` tags, no ES modules — `type="module"` has stricter `file://` restrictions in some browsers and this app needs to double-click-and-open cleanly.

### Deployment

The web app is published via GitHub Pages at `https://synthux-academy.github.io/svg2kicad/`, served straight from the `main` branch root — any push to `main` redeploys automatically, no build step. The repo is public (required for Pages on this org's free plan).

## Git workflow

After making changes in this repo, commit and push to `main` without stopping to ask for confirmation first — the user has explicitly asked for this every time, so no need to re-confirm per change. Since a push to `main` immediately redeploys the live web app (see "Deployment" above), only do this for finished, working changes, not mid-task experiments.

## Keeping docs in sync

When you add a feature or change behavior (new layer options, a different outline-detection rule, a new clipboard fallback, etc.), update `README.md` (user-facing usage) and this file (architecture/behavior notes) in the same change — don't leave them describing the old behavior.
